# 直播接收与转发使用文档

本功能使用独立的 MediaMTX 1.21.3 接收 WHIP 推流、通过 WHEP 提供 WebRTC 观看。推流与播放统一使用“系统设置 → 直播 API Key 管理”中的全局 `live_…` 密钥，不绑定考试；同一密钥也可读取本服务器所有考试的监考直播。它不授予监考客户端推流权限或后台管理权限。内网、公网各自管理密钥和媒体，不通过考试同步转发视频。

## 页面与密钥

- 系统设置负责生成、启停、删除及再次复制 API-KEY。新密钥使用 AES-256-GCM 加密保存、SHA-256 摘要鉴权。再次复制仅超级管理员可操作，普通列表不包含明文、摘要或密文。
- 升级前的系统密钥仅保存过摘要，仍可继续凭已保存的明文使用，但无法从摘要还原。如果需要再次复制，请新建密钥后将接入方切换到新密钥；不会自动作废旧密钥。
- 直播管理先由管理员新建流 ID，再展示已创建 ID 的推流状态、正在推流数量和对应播放 API 链接，不自动加载视频。选择系统密钥后可复制包含密钥的完整播放或推流链接。没有另设转发密钥或考试绑定。
- 新版不再接受旧的 `relay_…`、`relay_read_…` 转发专用密钥，旧 RTMP/HLS 接入方须切换为 WHIP/WHEP。

## 推流

WHIP 地址（`STREAM_ID` 为自定义流 ID，只能包含字母、数字、下划线、连字符，最长 64 字符；推流、播放和后续重连时大小写必须一致）：

```text
https://proctoring.example.org/api/live-relay/publish/STREAM_ID?apikey=系统API_KEY
```

也可以不在 URL 中携带密钥，改用 `Authorization: Bearer live_…`。两种方式二选一，不能混用。OBS 选择支持 WebRTC 的 WHIP 服务，将不含查询参数的上述地址作为服务器地址，将系统 API-KEY 填入 Bearer Token。其他直播系统需支持 WHIP；将 RTMP URL 文本改成 HTTPS 不能自动转换协议。

1. 对推流地址 `POST`，`Content-Type: application/sdp`，正文为发布者的 SDP offer。
2. 返回 `201`、SDP answer 和 `Location`。设置 answer 后，对返回的 Location 发送后续 ICE `PATCH`，停止时 `DELETE`。
3. `PATCH` 使用 `application/trickle-ice-sdpfrag`、`If-Match: *`。后续请求继续使用与首次相同的 API-KEY，或继续携带原查询参数。
4. 必须先在直播管理中创建流 ID，未创建的 ID 返回 404，不会自动登记。同一 ID 只允许一个发布连接，预留中的连接也占用名额；第二台设备或另一个密钥的重复推流返回 429，不替换已经存在的推流。旧连接关闭并被确认回收后，才允许再次连接。媒体服务同时禁止覆盖发布者，作为第二层保护。

系统设置中的全局密钥均可发布后台已创建且尚未被其他设备占用的转发流 ID。对推流端应只发放可信密钥，因为它同时具有全考试监考画面的读取权限。

## 播放

```text
https://proctoring.example.org/api/live/STREAM_ID?apikey=系统API_KEY
```

- 用浏览器打开，或作为 OBS 的浏览器来源，接口先换发短期播放凭据并跳转到 WebRTC 播放页。
- `GET` 加 `format=json` 返回 `{ok:true,data:{id,url,protocol:"webrtc",signaling:"whep",expiresIn:86400}}`。`url` 是带播放授权的观看页，同时可以直接作为 WHEP 信令入口，不是 m3u8 地址。
- 自行集成 WHEP：向同一播放入口 `POST application/sdp` 接收端 offer，处理 `201` 的 answer 和 `Location`；后续 ICE 和释放连接使用返回的 Location。支持跨域的 `POST/PATCH/DELETE/OPTIONS`。
- 播放页默认静音，可在播放器控制栏开启声音。断网、源流中断或媒体服务重启后会重连，失败重试采用带随机偏移的有界退避；旧连接会被释放或由后台回收。
- 停用或删除系统密钥会拒绝新请求，并尝试断开该密钥建立的监考观看及转发推流/观看连接，不中断考生的原始监考推流。失败时设置仍保留为停用，转发连接由后台继续重试清理。

推流和播放密钥相同，但后端会区分发布、读取及各条连接的资源权限，播放凭据不能作为推流授权，也不能操作其他连接。

## 低延迟与容量

采用 WebRTC 原始媒体转发，不启动转码、不生成 HLS 分片或多秒播放缓冲。优先使用 UDP，TCP 用作受限网络下的后备；浏览器支持时设置较低的抖动缓冲目标。实际延迟取决于推流端采集/编码、网络、浏览器和服务负载，未经过实际测量不能保证固定毫秒数。

建议源端启用低延迟编码，关闭 B 帧与前瞻缓存，使用浏览器支持的 H.264/VP8 视频和 Opus 音频。码率、分辨率和帧率应与上行带宽匹配。网络丢包时，不应通过不断增加缓存来累积观看延迟。

媒体数据不经过 Node 后台。信令及媒体鉴权采用不同的有界并发队列，避免协商等待自己的鉴权回调。推流和观看连接在数据库中预留名额，预留超时、断线、权限撤销及后台重启后由每 5 秒的独立任务回收。失败的断开记录保留供重试；容量达到上限返回 429，不无限堆积连接。正常连接最长 24 小时，需长期连续推流的来源应启用 WHIP 自动重连。

默认同时登记 8 路直播、允许全服务 16 个观看连接。流 ID 不会因尚未推流或暂时断网而自动删除。管理员可以在直播管理中归档不再使用的 ID 释放登记名额；归档会停止该流，且原 ID 不能重新创建，避免旧播放授权被复用到新画面。媒体服务独立限制 CPU、内存、进程数，不占用监考媒体服务的端口与会话。

## 部署

先备份数据库及环境配置，再执行一次 [数据库升级 SQL](../deployment/migrations/20261105-live-relay-webrtc.sql)。新增加密密钥列、独立的 WebRTC 连接表，并允许旧转发登记的密钥关联为空；不删除原有密钥或考试数据。也可使用项目的完整 schema 升级流程。

在原环境中保留已有 `LIVE_RELAY_AUTH_SECRET`，新增：

```dotenv
LIVE_RELAY_ADDITIONAL_HOSTS=203.0.113.10
LIVE_RELAY_ICE_PORT=1940
LIVE_RELAY_MAX_STREAMS=8
LIVE_RELAY_MAX_CONNECTIONS=16
```

内网对应服务器使用 `LIVE_RELAY_ADDITIONAL_HOSTS=192.168.50.20`。地址必须是观看、推流设备能够到达的本服务器地址，不能复制另一端的地址。内网浏览器还可能要求用户允许站点访问本地网络。

使用更新后的 `docker-compose.live-relay.yml` 与原 Compose 文件、原主机覆盖文件一起启动 `web` 和 `relay-media`。既有部署不要直接使用基础文件中会运行数据库初始化的启动命令，保留现有正常运行的后台 command。旧 `relay-gateway` 可单独停止；不要使用会影响其他服务的全栈停止命令。

Caddy 继续代理已有 HTTPS 后台，无需为 WebRTC 新开 HTTP 端口。移除旧 `/relay-stream/* → 8090` 的 HLS 专用处理规则即可，原监考媒体的 443 和内网 18189 转发保持原样。转发直播媒体使用 **1940/UDP 和 1940/TCP**；云安全组及主机防火墙都需放行，UDP 对低延迟尤其重要。信令使用 HTTPS，不应将 ICE UDP 当作普通 HTTP 反代。

后台内部通过 `http://relay-media:8889` 协商，通过 `:9997` 管理。内部端口不直接对公网开放，媒体回调使用独立随机鉴权值与每条连接的短期签名。长期系统 API-KEY 不传给媒体服务。WHIP/WHEP 资源 secret 与管理 API 的连接 ID 分别存储，撤销权限时使用正确的管理连接 ID。参考 [MediaMTX 1.21.3 信令实现](https://github.com/bluenviron/mediamtx/blob/v1.21.3/internal/servers/webrtc/http_server.go)。

`SESSION_SECRET` 同时用于保护可重复复制的密钥，应稳定保存并随配置备份。更换它后，原摘要鉴权仍可接受接入方保存的正确密钥，但原密文无法再次解密。
