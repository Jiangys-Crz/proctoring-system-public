# 直播接收与转发使用文档

考生监考与直播转发共用现有 MediaMTX。考生使用 `live/`、实时通话使用 `voice/`、转发直播使用 `relay/` 路径，分别鉴权。系统直播 API-KEY 只能按原规则读取监考画面及访问转发直播，不能替代考生或通话发布凭据。公网、内网各自运行自己的媒体服务，考试同步不传输视频。

## 创建直播及密钥

在“系统设置 → 直播 API Key 管理”生成或选择已启用的系统密钥，再在“直播管理”创建流 ID。流 ID 支持字母、数字、下划线和连字符，最长 64 字符，区分大小写。新建、归档、密钥复制沿用超级管理员权限。

同一个流 ID 同时仅允许一个发布者，WHIP、RTMP、RTMPS 共用该名额。正在连接也占用名额；其他设备不能覆盖原推流。归档会停止该流，原 ID 不可重新创建。旧的 `relay_…`、`relay_read_…` 专用密钥不再使用；当前接口使用系统 `live_…` 密钥。

## WHIP 推流

```text
https://proctoring.example.org/api/live-relay/publish/STREAM_ID?apikey=系统API_KEY
```

内网将域名换成 `proctoring.example.test`。OBS 服务选择 WHIP。完整地址含 `apikey` 时，Bearer Token 留空；也可移除查询参数，把 API-KEY 填入 Bearer Token，两种方式不能混用。

首次请求为 `POST application/sdp`，成功返回 `201`、SDP answer 及 Location。ICE 补传使用同一 Location 的 `PATCH application/trickle-ice-sdpfrag`；停止使用 `DELETE`。后续请求继续携带同一授权。停止成功及已回收连接的授权重复停止均返回 OBS 可识别的 `200`；仍存在的连接必须通过所属流、协议、密钥及凭据检查。

## RTMP / RTMPS 推流及读取

直播管理会显示本服务器的实际 RTMP、RTMPS 基址，并提供复制流密钥按钮。例如：

```text
RTMP 服务器：rtmp://proctoring.example.org:1940/relay
RTMPS 服务器：rtmps://proctorstream.example.org:443/relay
流密钥：STREAM_ID?apikey=系统API_KEY
```

内网可使用 `rtmp://192.168.50.20:1940/relay`，或页面显示的内网基址。OBS 选择自定义 RTMP 服务，把服务器与流密钥分别填写。RTMPS 使用服务器已有的媒体 TLS 入口；内网证书需要由设备信任。

支持 RTMP / RTMPS 的播放器可使用完整地址读取同一直播：

```text
rtmp://proctoring.example.org:1940/relay/STREAM_ID?apikey=系统API_KEY
```

读取也需要有效系统密钥，占用转发观看连接名额。裸 RTMP / RTMPS 不开放考生 `live/` 或通话 `voice/` 路径；它们继续执行各自原有授权规则。

媒体原样转发，不自动转码。浏览器 WebRTC 播放要求兼容的编码（常用 H.264 / VP8 视频及 Opus 音频）。普通 RTMP 的 AAC 音轨不属于 WebRTC 音频格式；需要浏览器音频时，使用 WHIP + Opus，或由支持 Opus 的 RTMP 推流端发送。RTMP / RTMPS 播放器可按自身能力直接播放 AAC。

## 浏览器播放

```text
https://proctoring.example.org/api/live/STREAM_ID?apikey=系统API_KEY
```

浏览器打开后换发短期播放授权并播放 WebRTC，默认静音，可使用播放器控制栏开启声音。API 加 `format=json` 可取得播放 URL；它不是 m3u8。自定义接收端使用 WHEP POST、PATCH 与 DELETE；支持跨域信令。播放票据不能用于发布。

未收到推流时明确显示等待 OBS 或其他设备开始推流；权限失效会提示授权错误。断网、源流停止后采用有界退避重连，旧连接会释放或由后台继续回收。

## 启动、回收与容量

考生及转发媒体配置都显式设置 `webrtcTrackGatherTimeout: 15s`，避免 OBS 或采集设备还未产出首包就在默认两秒后断开。该设置只放宽首次数据等待，不添加正常播放缓冲，始终没有数据的连接仍会超时释放。

转发连接按 WebRTC / RTMP / RTMPS 的实际媒体会话列表核对，不根据是否已出现媒体路径推断连接是否存活。容量检查通过同一数据库锁执行，默认最多登记 8 路流、16 个转发观看连接；不同协议合计计数。RTMP 回调还核对私有媒体 API 中真实存在的连接 ID，防止伪造回调占用名额。停用密钥或归档时只断开对应的转发连接及原有密钥观看连接，不停止考生发布。清理失败保留待回收状态，由后台重试。

共用服务承载监考及转发负载，应按实际人数、码率和硬件安排容量；代码核对及构建不能证明实际并发容量。

## 部署与升级

先备份数据库、配置及当前媒体配置，应用 [协议字段升级 SQL](../deployment/migrations/20261106-shared-media-relay.sql)。升级只新增协议字段和索引，原记录默认标为 WebRTC，不删除考试、密钥、直播登记或录像。

使用更新的基础 Compose、主机覆盖文件及 `docker-compose.live-relay.yml`。转发复用 `MEDIA_WHIP_INTERNAL_BASE`、`MEDIA_API_INTERNAL_BASE`、媒体管理签名及 `/api/media/auth`；原 `LIVE_RELAY_AUTH_SECRET` 必须保留，以保护已有播放及信令票据。基础媒体配置为 `relay/` 单独设置禁止覆盖发布者、禁止录像，考生路径保留原规则。

升级前停止旧 `relay-media`、`relay-gateway`，释放旧 1940 端口，再切换后台与共用媒体服务。保留旧容器、配置和镜像用于回滚，不使用全栈停止或清理卷。现有部署的后台 command 不改成执行初始化/种子数据的命令。主机上有正在推流的考生时，应安排切换时段。

转发原生 RTMP 通过 `LIVE_RELAY_RTMP_PORT`（默认 1940/TCP）映射到共用媒体的 1935；需要相应主机及云端放行。WebRTC 改用原有监考媒体的 ICE 通道，公网通常为 TCP/UDP 443，内网保留原有 18189 规则，使用 `browserIceAnswer` 处理内网端口。原 1940/UDP 不再承载转发 WebRTC。RTMPS 使用原有 Caddy 媒体 TLS 入口，无需新建证书站点。

`LIVE_RELAY_RTMP_PUBLIC_BASE` 可显式设置页面显示的 RTMP 基址；未设置时使用后台域名及配置端口。`MEDIA_RTMPS_PUBLIC_BASE` 决定 RTMPS 基址。保留各服务器自己的域名、证书、账号及密钥，不复制另一端的私有配置。
